## Schema & API Contracts

### 1. Response cleanup contract (behavioral, no new API)

**Parties:** `AsyncClient` request dispatcher ↔ `AsyncResponse.aclose()`

**Existing behavior (broken):**
- `AsyncClient.get(url)` initiates request, response starts streaming
- User code wraps call in `asyncio.wait_for(client.get(url), timeout)`
- Timeout or cancel fires during streaming
- Response stream is **not** closed
- Connection remains marked as in-flight
- `async with AsyncClient` exit raises `RuntimeError: The connection pool was closed while 1 HTTP requests/responses were still in-flight.`

**Required behavior (fix):**
- `AsyncClient` request dispatcher catches `CancelledError` and `TimeoutError` during response streaming
- Dispatcher calls `await response.aclose()` before re-raising exception
- `response.aclose()` closes stream and returns connection to pool atomically
- `async with AsyncClient` exit completes cleanly, no `RuntimeError`

**Method signature (existing, no change):**
```python
class Response:
    async def aclose(self) -> None:
        """Close response stream and return connection to pool. Idempotent."""
```

### 2. Sync/async parity contract

**Parties:** Sync `Client` ↔ Async `AsyncClient`

**Contract:**
- Both must implement identical cleanup logic for interrupted response reads
- Sync: `response.close()` called on interrupt (e.g., `KeyboardInterrupt`)
- Async: `response.aclose()` called on `CancelledError`/`TimeoutError`
- Both must suppress in-flight connection error on client context exit after cancel/timeout

**No new API; behavioral alignment only.**

## Risks

### Risk 1: Cancel raised after response.aclose() already called
**Likelihood:** Low  
**Impact:** Low (double-close is safe if `aclose()` is idempotent)  
**Mitigation:**
- Verify `response.aclose()` is idempotent (check `httpx/_models.py`)
- Add test in `test_async_client_cancel.py`: call `aclose()` twice, assert no error
- **Detection:** Code audit of `Response.aclose()` implementation
- **Fallback:** Add idempotency guard if missing (e.g., `if self._closed: return`)

### Risk 2: Timeout fires in the middle of aclose() itself
**Likelihood:** Low  
**Impact:** Medium (connection might not return to pool if `aclose()` is interrupted)  
**Mitigation:**
- Audit `Response.aclose()` to check if pool return is shielded from cancellation
- If not shielded, wrap pool return in `asyncio.shield()` or equivalent
- Add test: cancel while `aclose()` is executing, verify pool state after
- **Detection:** Trace `aclose()` → pool release code path; check for `try/finally` or shield
- **Fallback:** Add shielding to pool return section of `aclose()`

### Risk 3: Sync client diverges from async client in cleanup logic
**Likelihood:** Medium (if fix only touches async code)  
**Impact:** High (AC-3 failure)  
**Mitigation:**
- Review sync `Client` code path for same issue (search for `response.read()` or equivalent)
- Apply parallel fix in `httpx/_client.py` (sync) if issue exists
- Add sync tests in `test_client_cancel.py` mirroring async tests
- **Detection:** Reproduce issue with sync `Client` + threading/interrupt
- **Fallback:** None; sync fix is mandatory per AC-3

### Risk 4: Existing code assumes response auto-closes on context exit
**Likelihood:** Medium  
**Impact:** Medium (potential double-close or missed cleanup elsewhere)  
**Mitigation:**
- Grep for `async with response` and explicit `aclose()` calls in httpx codebase
- Check `Response.__aexit__` implementation; ensure it calls `aclose()` (should already)
- Verify new cleanup does not conflict with `__aexit__` behavior
- Add test: use `async with response` after cancel, verify no double-close error
- **Detection:** Code audit + test
- **Fallback:** Document interaction; ensure idempotency handles overlap

### Risk 5: Fix introduces performance regression in normal (non-cancelled) flow
**Likelihood:** Low  
**Impact:** Low (try/except overhead is negligible in Python async)  
**Mitigation:**
- Measure baseline request latency before fix (if perf tests exist)
- Re-measure after fix; flag if >5% regression
- **Detection:** Perf test suite (if available) or manual benchmark
- **Fallback:** Profile and optimize if regression found; unlikely given try/except is cheap
